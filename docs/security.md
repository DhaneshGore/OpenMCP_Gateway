# Security

This document describes the gateway's security model, its defaults, and what
you must still do yourself. To report a vulnerability, see
[SECURITY.md](../SECURITY.md).

## Trust boundaries

| Party | Trusted? | Notes |
| --- | --- | --- |
| Operator (config file, gateway environment, admin tokens) | yes | Can run arbitrary commands via stdio server definitions. |
| MCP client | authenticated, then authorized per server | All input is untrusted. |
| stdio upstream process | runs with the gateway's OS privileges | Its output is untrusted (size-limited, parsed defensively, schema-validated). |
| Remote upstream | untrusted network peer | Reached only through the egress guard. |

**The gateway is not a sandbox.** A stdio server can do anything the gateway's
OS user can. Run untrusted servers in containers or as a separate user.
Docker is described in [deployment.md](deployment.md).

## Defaults

| Default | Why |
| --- | --- |
| Bind `127.0.0.1` | Nothing is reachable from the network until you choose so. |
| `auth.mode: none` refused on non-loopback addresses | Avoids accidentally running an open proxy. Override: `auth.allow_unauthenticated_non_loopback`. |
| No default credentials | Tokens are created with `openmcp token generate`; only hashes are stored. |
| Admin API always needs an `admin`-role token | Even when MCP traffic is unauthenticated. |
| No stdio registration through the admin API | It would be remote code execution. Opt in with `admin.allow_stdio_registration`. |
| Remote upstreams limited to public addresses | SSRF protection; see below. |
| Minimal subprocess environment | Gateway secrets are not inherited by servers. |

## Authentication

`auth.mode: bearer` accepts `Authorization: Bearer <token>`. Tokens are opaque
gateway API keys: 256 random bits with an `omg_` prefix, generated by
`openmcp token generate`. The config stores `sha256(token)`. These are **not**
OAuth access tokens. They have no audience or expiry, and the gateway treats
them as a separate credential type. An OAuth 2.1 resource-server mode is
planned.

Rotation: generate a new token, add its entry next to the old one (names must
be unique, e.g. `laptop-2026-10`), restart, move clients over, then delete the
old entry and restart. Revocation is removing the entry and restarting.

Identity headers (`X-Forwarded-User`, `X-Remote-User`, …) are **never** used.
`X-Forwarded-For`/`-Proto` are honoured only from `gateway.trusted_proxies`.

## Authorization

* Each token lists the server ids it may use (`servers: ["*"]` for all).
* `tools/list`, `prompts/list` and `resources/list` only include permitted
  servers. Calls to a forbidden server receive exactly the same error as
  calls to a non-existent one, so authorization doesn't reveal which servers
  exist.
* Per-server tool filters (`servers[].tools.allow/deny`) apply to everyone.
* Roles: `admin` (admin API), `metrics` (only `/admin/metrics`).
  `openmcp token generate --admin` gives admin tokens no MCP server access
  unless you add `--server`.
* Unauthenticated endpoints (`/health`, `/ready`, `/version`) expose no server
  ids, only counts and versions.

## Sessions

The SDK generates session ids with `uuid4` (unpredictable). Each session is
bound to the principal that created it; a request presenting a different
credential with that session id receives 404. Sessions expire after
`limits.session_idle_timeout` and are capped by `limits.max_sessions`.
Session state lives in process memory.

## Subprocess environment

A stdio server receives only:

* `PATH`, `HOME`, `USER`, `LOGNAME`, `LANG`, `LC_ALL`, `LC_CTYPE`, `TMPDIR`,
  `TZ` (on Windows, the equivalent system variables);
* variables named in `inherit_env`;
* literal `env` values;
* `env_from_host` values, copied from the gateway's environment by name and
  registered for redaction.

Commands run with an argument vector (`execve`), never through a shell, so
shell metacharacters in `args` are passed literally. NUL bytes are rejected.

## Packages

Uploaded packages are untrusted input until an operator decides to run them,
and untrusted code once they run. Validation, immutable digests, verification
before every start, hash-locked wheel-only dependencies, per-instance
directories, and a Landlock + seccomp sandbox reduce what a package can do:
it cannot read other servers' files, the artifact store, the catalog, the
gateway's configuration or `/proc`, and cannot open UNIX sockets.

It is **not** a complete isolation boundary. Packages run as the gateway's
OS user (signals are not isolated before Linux 6.12), may use the network
unless `network: deny` (including cloud metadata endpoints and `localhost`
services), and have no CPU/memory quotas unless you configure them or use a
container. The full list is in
[packages.md](packages.md#limitations-read-before-running-untrusted-packages).

## Outbound connections (SSRF)

Remote upstream URLs are validated when configured (scheme, no embedded
credentials) and **again at every connection**:

1. The hostname is resolved.
2. Every resolved address must be allowed. If any address is internal, the
   connection is refused, so mixing public and private DNS records doesn't
   get through.
3. The socket connects to the validated address itself, not the hostname, so
   DNS rebinding between check and use has no effect. TLS still verifies the
   certificate for the original hostname.
4. Redirects open new connections and pass through the same check. In
   addition, the SDK only follows same-origin redirects.

Allowed by default: globally routable addresses. Blocked: loopback, RFC 1918
private, link-local (including `169.254.169.254` metadata), carrier-grade
NAT, unique-local IPv6, multicast, unspecified, reserved and documentation
ranges. IPv4 addresses embedded in IPv6 (mapped, 6to4, Teredo, NAT64) are
unwrapped first.

Exceptions for trusted internal deployments:

* `security.allowed_egress_networks: ["10.20.0.0/16"]` permits specific
  ranges for all remote upstreams;
* `servers[].allow_private_network: true` permits any non-public address for
  one server (logged as a warning by `config validate`).

Environment proxy settings are ignored for remote upstreams.

## Resource limits

| Limit | Setting |
| --- | --- |
| Client request body | `limits.max_request_body_bytes` (413) |
| Upstream message size | `limits.max_upstream_message_bytes` (stdio line, SSE event, JSON body) |
| Items per upstream listing | `limits.max_tools_per_server` |
| In-flight requests per server | `servers[].max_concurrency` |
| Waiting requests per server | `servers[].max_queue`, `servers[].queue_timeout` (error `-32011`) |
| Request rate | `rate_limits.*` (error `-32012`) |
| Sessions | `limits.max_sessions` (503) |
| Captured stderr | `logging.stderr_buffer_lines` × `logging.stderr_line_bytes` |
| Restarts | `servers[].restart.*` |

## Logging and redaction

* Logs are structured; every request carries an `X-Request-ID`.
* Redaction removes the values of every `env_from_host`/`headers_from_host`
  secret, plus common credential patterns (`Bearer …`,
  `Authorization: …`, `api_key=…`, well-known token prefixes). It is applied
  to all log records and to captured stderr.
* The gateway does not log tool arguments or results.
* Errors sent to clients are written by the gateway; exception text and
  upstream stderr never reach clients. Upstream JSON-RPC errors are forwarded
  with their original code, message and data.

Pattern-based redaction is best effort. Don't rely on it to hide secrets
that servers print in unexpected formats.

## Hardening checklist for network deployments

- [ ] `auth.mode: bearer`, one token per client, least-privilege `servers` lists
- [ ] TLS in front of the gateway (reverse proxy), `gateway.allowed_hosts` set
- [ ] `gateway.trusted_proxies` set to the proxy's address only
- [ ] `rate_limits` configured
- [ ] stdio servers run in a container or as an unprivileged user
- [ ] admin token stored separately from client tokens; `metrics` role for scrapers
- [ ] `admin.allow_stdio_registration` left `false`
- [ ] if packages are enabled: `auth.mode: bearer`; a dedicated gateway user that is not in the `docker` group; `sandbox.isolation: landlock`; `dependencies.policy: locked` with an internal `index_url`; `network: deny` wherever possible; no reachable cloud metadata credentials; container/cgroup CPU and memory limits
- [ ] logs shipped to a store with access control
